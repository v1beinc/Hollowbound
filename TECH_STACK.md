# Hollowbound — предпочтения по стеку и архитектуре

Дата решений: 2026-09-30. Статус: технический план. Новые пакеты, потоки и модели ниже ещё не внедрены, если явно не отмечено текущее состояние.

## Основной выбор

Предпочтение: локальное приложение C#/.NET 10 + MonoGame DesktopGL и самостоятельное детерминированное ядро симуляции. Этот стек уже работает в репозитории и позволяет контролировать порядок решений, сохранения, производительность и headless-прогоны. Развитие экономики и интеллекта происходит внутри того же runtime.

| Область | Предпочтение | Причина и состояние |
|---|---|---|
| Runtime | C#, .NET 10 LTS | Текущее `net10.0`; SDK зафиксировать в `global.json` после проверки установленной версии |
| Клиент | MonoGame DesktopGL, SpriteBatch, существующий UI/layout | Текущие пакеты Framework/Content Builder Task `3.8.5.1`; обновление отдельным проверяемым изменением |
| Content tools | MGCB через `.config/dotnet-tools.json` | Текущие локальные tools `3.8.5`; согласовать обновления инструментов и runtime, хранить manifest |
| Модель мира | Дискретная симуляция агентов, производственные/социальные графы | Экономика и организации реализуются как предметные системы C# |
| Решения агентов | Utility AI, ограниченное GOAP-планирование, обучение по результатам | Utility biases уже есть; планировщик и новые цели предстоит добавить |
| Экономика | Целые единицы/фиксированная точность, инвентари, журнал согласованных операций | Новое ядро для производства, обмена, собственности и контрактов |

| Аналитика | Существующий JSONL + графики и карты в игре | Текущая schema v5; SQLite добавлять только при доказанной потребности в запросах по большой истории |
| Масштаб | Чанки, spatial indexes, buffers, распределённые по тикам обновления, затем когорты | Часть уже реализована; экономические приближения и фоновые бюджеты предстоит проверить |
| Замеры | Текущий profiler/headless benchmark, при необходимости BenchmarkDotNet | Разделять microbenchmark, симуляцию и GUI FPS |
| Доставка | Self-contained папка Windows x64, ZIP; CI через GitHub Actions | Pipeline и publish smoke-check ещё предстоит создать |
| ML-исследование | Python/PyTorch для обучения общей политики, ONNX Runtime в C# | Условное расширение после измеренного ограничения базового AI |

[Официальная политика .NET](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core) на дату проверки относит .NET 10 к LTS. Runtime в self-contained сборках обновляется выпуском новой сборки игры. [Документация MonoGame](https://docs.monogame.net/articles/tutorials/building_2d_games/01_what_is_monogame/) описывает framework и его контролируемую разработчиком архитектуру.

## Предметные границы и последовательность выделения

Текущий проект сохраняется рабочим. Сначала отделить экономические операции и агентные решения в небольшие типы/системы внутри `Simulation/`; разделение на проекты оправдать независимыми headless-проверками и зависимостями.

Целевая структура модулей:

```text
Simulation/
  World / Timing / Rules
  Agents / Perception / Memory / Decisions / Learning
  Economy / Inventories / Production / Logistics / Ledger
  Organizations / Ownership / Jobs / Contracts / Governance
  Knowledge / Communication / ComputeInfrastructure
  Settlements / Regions / Relations
  Events / Analytics / Persistence
Client: Game1 + Experience / Rendering / UI / Input / Audio
Headless: Scenarios / Benchmarks / ReplayChecks
```

Типы имеют стабильные ID; ссылки между агентами, складами и организациями сериализуются по ID. Объекты и ресурсы имеют владельца, а владение и права пользования задаются отдельно. Изменение мира выполняется через явные операции; UI отправляет команды и читает представление.

Системы запускаются в фиксированном порядке по simulation ticks: принять команды → обновить наблюдения → выбрать цели → обработать перемещение/работу → выполнить согласованные операции → оценить результаты → обновить организации и знания → записать события. Конкретный порядок утверждается перед экономическим срезом и фиксируется в ruleset.

## Разум: планирование плюс опыт

Utility AI оценивает несколько целей с учётом потребностей, интересов организации, риска и памяти. GOAP строит короткую цепочку разрешённых действий, например добыть → доставить → получить доступ к материалу → построить. Число раскрытых состояний, длина плана и частота перепланирования ограничены детерминированными бюджетами. На исчерпании бюджета выполняется понятная базовая политика; wall-clock влияет на диагностику, а не на выбор действия.

Планы сохраняют версию, использованные сведения и причину выбора. Новое наблюдение инвалидирует устаревший план. Учёт фактического результата обновляет предпочтения; цель обучения включает выживание, успешные поставки и эффективность, с раздельными показателями потерь и ошибок. Случайные решения используют сохранённое состояние RNG и стабильный порядок ID.

Организационный планировщик распределяет задачи и ресурсы на более редких тиках. Агенты имеют локальные сведения; сведения о других организациях приходят через наблюдения и сообщения. Коллективная память хранит происхождение, давность, уверенность и проверки знания.

Первоисточник подхода: [Jeff Orkin — Three States and a Plan](https://pages.cs.wisc.edu/~dyer/cs540/handouts/gdc2006_orkin_jeff_fear.pdf). GOAP — метод планирования; его сочетание с обучением и экономикой является нашим проектным решением.

## Экономические контракты

Количество товаров и балансы учитываются в `long` минимальных единицах с проверкой переполнения; дробные цены используют явно установленный масштаб. Воспроизводимость расчётов проверяется в пределах поддерживаемой сборки/runtime; существующие float-поля агентов не переписываются массово ради этого решения.

Операция содержит ID, tick, инициатора, участников, входы, выходы и причину. При оплате/обмене применяется единый commit после проверки резервов; повтор операции распознаётся по ID. Валютный перевод балансирует дебет и кредит, а эмиссия/сжигание имеют отдельную разрешённую операцию. Резервы и находящиеся в пути товары учитываются отдельно от доступных запасов.

Длительное производство хранит задание и прогресс. Остановка по нехватке энергии, отмена контракта, смерть владельца задачи и смена организации имеют явные правила освобождения резервов. Производственные рецепты задаются в валидируемых versioned JSON definitions с набором разрешённых действий, диапазонами и checksum ruleset.

## Потоки, фон и детерминизм

Сначала оптимизировать реальные горячие участки по данным текущего профайлера. На отдельный simulation worker переходить, когда это помогает выдержать GUI-бюджет. Предпочтение — один поток, владеющий world state, ограниченная очередь команд и неизменяемые снимки для render/UI; GPU-операции остаются на потоке MonoGame.

Команды получают ID и целевой tick; очередь сохраняется там, где влияет на продолжение мира. Пауза подтверждается на границе тика. Сохранение снимает согласованный world snapshot, затем запись выполняется отдельно; закрытие окна ждёт подтверждения сохранения или сообщает ошибку.

Бюджеты AI задаются числом операций и распределением обновлений по тикам. Бюджеты рендера и фонового throughput могут зависеть от реального времени. Журнал RNG, команд, ruleset и tick используется для воспроизведения в одной совместимой версии. Межверсионный и межплатформенный bit-exact replay требует отдельного доказательства.

LOD может агрегировать когорты, но обязан учитывать производство, расход, ресурсы в пути и договоры. Камера не должна создавать или уничтожать богатство. Экономическое развитие при разных траекториях камеры проверяется на фиксированных сценариях; допустимые приближения макромодели явно документируются.

Полный ECS-framework добавлять только после сравнительного замера памяти/throughput на репрезентативном мире. На первых версиях достаточно последовательных массивов/списков, устойчивых индексов, повторно используемых буферов и ограниченного планирования. Потокобезопасные коллекции сами по себе не дают воспроизводимость.

## Persistence и аналитика

Текущее сохранение пишет JSON во временный файл и заменяет целевой файл. Следующая итерация добавляет проверенную backup/recovery-логику и версионирование ruleset. Читатель отклоняет неизвестную будущую версию; старый файл копируется перед миграцией. Ошибка миграции оставляет исходник доступным.

Продуктовая версия, `WorldSnapshot.Version`, версия аналитики и ruleset — разные идентификаторы. Выпуск новой игры не означает автоматический переход к совпадающему номеру snapshot. Состояние планов, резервов, контрактов, памяти и отметок отсутствия сохраняется, если оно влияет на будущее.

JSONL содержит выборочные snapshots и значимые события с `event_id`, `run_id`, tick, ID организаций, причиной и измеренным результатом. Ограничивать объём, ротацию и число агентов в диагностике. Писать telemetry каждого решения каждого агента только в коротком диагностическом режиме.

Долгая Chronicle хранится отдельно от ограниченного окна UI. Отчёт о возвращении агрегирует события между контрольными tick, показывает полноту истории и пропуски. SQLite — возможный локальный read-model для поиска; авторитетное состояние мира остаётся в симуляции и versioned save. Сетевую отправку диагностики вводить через отдельный opt-in.

## Проверки и ограничения

Каждый поведенческий срез получает focused regression, save/load continuation и предметные инварианты: сохранность ресурсов, баланс валютных переводов, допустимые владельцы, освобождение резервов и корректные сроки. Старые сценарии сохраняются. Новые тесты добавляются для новых контрактов и рисков, а не для дублирования каждой функции.

Замеры включают фиксированные seed/ruleset/population/ticks и повторения после прогрева. GUI использует одинаковые разрешение, zoom и машину. [BenchmarkDotNet](https://benchmarkdotnet.org/articles/overview.html) подходит для повторяемых небольших замеров алгоритмов; FPS и длительные миры оцениваются отдельно.

Ориентиры до demo: основной GUI-профиль с 300 жителями, 1280×720, комфортный x1; стремиться к 60 FPS и реакции на паузу до 100 ms. Подтвердить достижимую фактическую скорость отдельно для каждого профиля. Фоновый прогон 2 часа и отдельный 8-часовой soak — будущие acceptance-проверки. Эти цели пока не являются результатами текущего пакета.

## Условное ML

Эксперимент оправдан конкретным провалом: базовая политика плохо адаптируется к изменению спроса или распределению ресурсов. Headless-среда экспортирует наблюдения, разрешённые действия и награды; train/holdout seed разделяются. Сравниваются восстановление, выживание, выпуск, latency и энергозатраты игры.

Предпочтение: Python/PyTorch для обучения одной общей политики с индивидуальными контекстами; экспорт модели и C# inference через ONNX Runtime. Стоимость inference измеряется в фоне и GUI. Весам, preprocessing и mapping действий присваиваются версии. На ошибке/исчерпании бюджета включается базовая политика; веса модели не изменяются незаметно в опубликованной сборке.

Источники: [PyTorch RL tutorial](https://docs.pytorch.org/tutorials/intermediate/reinforcement_q_learning), [ONNX Runtime C#](https://onnxruntime.ai/docs/get-started/with-csharp.html). Возможность запуска модели не доказывает пользу RL для Hollowbound. Введение моделей требует отдельного сравнения и проверки продолжения сохранения.

LLM можно исследовать для вариативного текста хроники поверх подтверждённых событий. Такая генерация остаётся представлением: экономика, причины событий и команды проверяются ядром. Первый релиз сохраняет возможность полной локальной игры без внешнего AI API.

## Сборка и выпуск

Windows x64 — первая поддерживаемая цель. Предпочтение — self-contained папка со всеми .NET и native-зависимостями, compiled Content и лицензиями. Single-file, trimming и Native AOT требуют отдельной проверки совместимости и не входят в первоначальную конфигурацию.

CI планируется на Windows runner с закреплённым SDK, tool restore, сборкой Content, headless regressions, publish и проверкой состава артефакта. Текущий `UIFont.spritefont` использует установленный Segoe UI: перед распределяемым/воспроизводимым build заменить его на включённый в проект шрифт с подходящей лицензией и проверить кириллицу. Конкретный font asset и его лицензия выбираются при реализации release pipeline.

Доступность на Linux/Steam Deck проверяется после Windows demo через отдельный RID и реальную графическую сессию. Магазинная интеграция остаётся адаптером к локальной игре. Практическая упаковка и публикация: [RELEASE_PLAN.md](RELEASE_PLAN.md).
